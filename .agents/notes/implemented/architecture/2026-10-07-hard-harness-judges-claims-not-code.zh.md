# Agent Note: hard harness 评判主张，而不是代码

Status: implemented

[English](2026-10-07-hard-harness-judges-claims-not-code.md) | 中文

## 问题

hard harness 的存在是为了让模型持续工作，直到任务真正完成。模型通过宣称“完成了”来停下——“我全扫过了，什么也没发现”——因此 harness 唯一的抓手是拒绝完成主张，而它只能拒绝自己能检查的东西。

覆盖交叉核查用固定的 sink 表 grep 一个模块，并把空 grep 读作干净。对一个含有五个真实 WordPress 漏洞的 PHP 文件运行（没有权限检查、SQL 拼进 `$wpdb->get_results`、`include $_GET`、任意文件写入、`passthru`），每个类别的模式都一无所获，而 `hard_clear_modules` 会把每个单元记录为 `model-verified`：全覆盖、零发现、harness 归因，落在有漏洞的代码上。验证器的三条 grep 还都带 `-I`，它按内容跳过二进制，与扩展名无关，因此共享库也会读作干净。另外，默认排除 glob 丢掉了 `vendor/`、`dist/`、`assets/` 等会进入生产的目录树，而武装记录从不说明这一点，所以覆盖率可能建立在被悄悄缩小的分母上。

## 决策

harness 评判主张，而不是代码。模型负责找 bug；harness 拒绝它无法支撑的完成主张，并且从不认证它没有检查过的东西。

- **发现与清除不对称。** 发现带有机器可检查的产物——PoC、它的标记、良性对照臂——并保持 `demonstrated`，绝不是 `proven`，因为 PoC 是模型写的。清除在任何语言里都没有机器见证，因此 harness 不认证清除。
- **grep 只能指控。** 模型未声明的命中会重开单元；空 grep 是沉默。因此 `model-verified` 表示批量筛查——模型未审读就清除、而 grep 一无所获的单元——这是最弱的模型级别，完成评估的审计下限只计入逐个裁决的模型单元与已解决的假设。
- **可筛查性是每个模块被记录的属性。** 武装时，`hard-mission` 通过与空树的 numstat 差异比较列出被固定提交的文件，同时标记二进制。一个非惰性模块只要含有二进制，或含有扩展名不在 `SCREENED_EXTENSIONS`（验证器的表，为 JavaScript 与 TypeScript 系列、Python 和 Java 编写）覆盖范围内的文件，就记入 `unscreenedModules`。分类同时看内容与扩展名，因为 `grep -I` 就是这样做的。`hard_clear_modules` 在任何 grep 运行之前拒绝这类模块，而在那里的模型清除会在台账、完成门决策记录、面板与试点报告中计为盲清除。
- **分母是被固定提交的全部内容。** `excludeGlobs` 默认为空；排除是部署方的显式选择，以计数和有界样本记录在武装事件中，并在覆盖率旁报告。500 行上限建议调粗 `moduleDepth`，从不建议丢弃代码。
- **首次武装时工作区必须与被固定的提交一致。** 模型读取的是工作区，而矩阵与引用按提交解析。加载只测量偏离而不失败——恢复的会话要在其自身运行产生的文件之上加载，包括 PoC，而 PoC 契约把它们放在目标之内——启动监听器拒绝在偏离的工作区上武装全新根代理。harness 自身的状态目录不算偏离。
- **逐格清除必须引用真实存在的代码。** 真实模型是逐格清除的，因此由这条路径承担成本：`cleared` 判定以 `path:symbol` 或 `path:line` 引用每个检查过的位置，验证器在记录写入之前只用 git 在被固定的提交上解析每个位置。这是防捏造的下限，而不是清除的证明——符号可能位于注释中——交叉核查按路径与符号或行号而不是按子串把 grep 行与引用匹配。
- **模型能读到它被推着走过的棋盘。** 除一个之外，每个 hard 工具都只写；转向指令只点名五个未覆盖单元，拒绝信息只点名十二行，在大仓库上这会把压力变成瞎猜。`hard_status` 回读按类别统计的未完成工作、完成门、矩阵轴，以及有界的一页棋盘单元或未完成条目。它返回计数，从不返回覆盖率：在承压的模型面前放一个醒目的进度数字，会诱使它为了数字去清除单元。

## 考虑过的替代方案

- **为 PHP、Go、Rust 等提供按语言划分的模式包。** 作为通往正确性的路线被否决：它让 harness 成为更好的 bug 猎手，而那是模型的工作，并且随语言数乘以类别数扩张，永远落后。一旦缺失的模式包被记录为不可筛查而不是读作干净，模式包就只是优化。
- **对模型批量模式做非空检查**（它们必须在仓库某处有命中）。作为信任门被否决：一个命中另一模块中无关字符串的模式就能通过，与 echo trap 和负对照阶梯一样，多写一行就被击败。
- **要求模型的模式命中它声明的 sink。** 被否决：模型的产物彼此一致什么也证明不了。
- **在 harness 中使用语言服务器。** 对 harness 而言被否决：LSP 报告符号与引用，而不是污点。它属于审读代码的 LLM 的工具箱。
- **加载时因偏离而失败。** 被否决：恢复的会话将无法在其自身的 PoC 文件之上加载。

## 后果

- 在模式表未覆盖的语言上，harness 现在报告“N 个盲清除”，而不是“100% 已验证”。纸面上的覆盖更少，但它是诚实的。
- 失败即关闭的分类很严格：带 `package.json` 或 `.gitignore` 的根模块、带 `.css` 的前端模块都不可筛查，因此在那里无法批量筛查，模型要逐格审读。
- 对含有随附目录树的目标，任务成本更高；成本是可见的，排除只差一条已配置的 glob。
- 独立审读者方向——harness 派生一个全新、对主张不知情的 LLM 来重读抽样的清除，并以固定在提交上的 worktree 作为隔离——是为清除建立见证的下一步；本笔记不包含它。
