# Agent Note: hard harness 根据 Joern 事实绘制功能地图

Status: implemented

[English](2026-10-10-hard-harness-maps-features-from-joern-facts.md) | 中文

## 问题

hard harness 按模块与缺陷类别做 source 到 sink 的扫描来找 bug。WordPress 7.1.3 任务的四个发现中有三个属于另一类：两个功能在不同的授权检查下触及同一状态（widgets REST 的 edit 上下文、无需 `edit_post` 即可更改附件的父文章、`find_posts` 返回草稿标题）。寻找这类问题需要目标的功能地图：每个功能由哪些函数实现、各自从哪里被调用、读写哪些状态、由哪些检查保护。模型可以边读边写这样的地图，但为了列出调用方而读完中等规模目标的每个函数，会耗掉任务的大部分 token 预算，而且只由模型写出的地图是 harness 无法检查的主张。

Joern 从源码构建代码属性图（语法树、控制流、调用图、数据流）并回答对它的查询。在 WordPress 7.1.3 上用 Joern v4.0.653 测得：1,516 个文件的 PHP 图约 30 到 60 秒建成，占用约 6 GB 内存；固定导出方法与调用点约需 30 秒；单个查询只需毫秒。PHP 调用图并不完整：在类内部调用的自由函数被解析为不存在的类方法（Joern issue 3050），因此 25 个 `wp_insert_post` 调用点只解析出 11 个；`array($this, 'method')` 这类数组回调被拆成临时赋值；`parent::`、后期静态绑定、变量调用与计算出的 hook 名称仍未解析。目标中重定义 WordPress 函数的 PoC 文件会截走 `check_ajax_referer` 等调用，直到把它们排除。

## 决策

Joern 提供事实；模型为功能命名并分组；harness 根据事实检查模型的功能主张。

- **Joern 事实是证据，绝不是判决。** 每条调用边都带有来源（`joern`、harness 修复、`grep`，或 harness 在固定提交上解析过的模型引用）。缺少 Joern 边本身绝不拒绝模型主张；图之外的主张必须改为引用调用点。
- **事实来自固定提交。** `hard-cpg` 用 `git archive` 导出固定快照，通过 shell seam 运行 PHP 前端与一个随包提供的查询脚本，并把 JSON Lines 输出按提交与查询摘要缓存在快照存储旁，因此事实与引用描述同一份内容。
- **只运行随包提供的查询。** Joern 的解释器执行任意 Scala，其服务器模式不是安全边界，因此模型和任何工具参数都不会到达 Joern；harness 用 harness 构造的参数运行随包脚本。
- **导出与框架无关。** 脚本输出文件、内部方法与调用点，附带已解析目标与有界的参数摘要，包括被脱糖的数组字面量的值。WordPress hook、REST 路由与权限检查等框架知识属于之后基于这些事实的配置档，而不属于 Scala 查询。
- **排除是显式的。** `excludePaths` 默认为空，与任务以整个提交为分母一致；快照中含有 PoC 桩的部署按路径排除它们。
- **由部署方安装 Joern。** bundle 以关闭状态挂载 `hard-cpg`；启用时必须提供 `joernHome`，构建脚本不会下载 1.7 GB 的发行包。
- **先做 PHP。** 首个导出面向 PHP 前端，因为测量的任务是 WordPress；其他前端在有各自测量后再加入。
- **修复是基于事实的规则，并且各自带标记。** `hard-featuremap` 只在事实恰好指明一个目标时，才为 Joern 未解析的调用加边，并标记为 `repair`（类型继承链、相对调用、issue 3050 的类限定自由函数）、`unique-name`（只有一个方法使用该方法名的动态调用）或 `hook`（字面 hook 触发到其注册的回调）。在 WordPress 7.1.3 上，这把 grep 找到的全部 24 个 `wp_insert_post` 调用点都链接上了。
- **功能地图数据库是派生数据。** 一个 SQLite 文件保存所有项目与快照，按目标根目录、提交与派生摘要作为键；因为事实随时可以再次导入，带有其他 schema 版本标记的文件会被删除并重建，而不是迁移。

## 考虑过的替代方案

- **只由模型绘制功能地图。** 不作为基础：靠阅读列出调用方会耗掉大部分预算，也让 harness 没有可用于检查完整性的依据。
- **用 Joern 自带界面或 Neo4j 导出做地图视图。** 被否决：Joern 没有 Web 界面，其导出显示的是语法与流节点，而不是功能、状态与授权，也无法链接到台账记录。
- **让模型直接查询 Joern。** 被否决：执行任意代码的解释器不是 harness 能够约束的工具参数。
- **tree-sitter 符号提取。** 推迟：它更轻量且支持多语言，但不提供调用解析或数据流；它保留为 Joern 读不好的语言的后备方案。
- **在 Scala 中修复 Joern 的 PHP 调用解析。** 被否决：修复放在基于导出事实的 TypeScript 中，由逐文件覆盖率与 fixture 测试。

## 后果

- 启用的部署需要 JDK 21、供 PHP 解析器使用的 PATH 上的 PHP、约 3.5 GB 磁盘用于 Joern，以及对 WordPress 规模的目标约 6 GB 量级的内存。
- 每个导出步骤都受 shell 单条命令超时上限约束；比 WordPress 更大的目标可能需要调高 shell 的 `maxTimeoutMs`。
- 功能地图的完整程度取决于图加引用；完整性检查对图能看到的边是严格的，其他地方则要求引用。
